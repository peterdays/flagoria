# Cut sync (two-player)

Drive: not player-facing

In a two-player game a tree or bush cut by any player becomes the same walkable stump on every peer (#223), and grows back on every peer at the same moment (#298). The cutter asks the host, the host decides and tells everyone, and only the cutter gets the wood. The host alone decides when a stump regrows. A player joining later gets the host's exact cut set with each cut's age. Chopping itself (taps, swings, sounds, regrowth offline) is in [Chopping trees and bushes](./chop-trees-and-bushes.md) and [Chop trees (live drive)](./chop-trees.md).

## Sub-features

- `cut-request` a client's chop ends in `Interaction._cut`, which sends `request_cut(cell)` to the host (`Scripts/mechanics/interact/interaction.gd`). The fall and pickup sounds play on the client at once; the stump and the wood follow one round trip later.
- `cut-decide` the host checks the cell against the generated map plus its cut list (`world.cut_grown`, `Scripts/mechanics/trees/tree_cuts.gd`), not its drawn tiles, so it can decide cells it has not drawn (and a dedicated server can). It first drops a request from a peer over its cut request limit ([Cut request limit](./cut-rate-limit.md), #355), then rejects a dead cutter ([Dead player cuts nothing](./dead-player-cut.md)), a cutter farther than `REACH` + `REACH_SLACK` (24 px) from the cell, and a cell already cut, so of two cuts of one cell only the first gets wood.
- `cut-apply` the host sends `apply_cut(cell)` to every peer, and `receive_yields(yields)` to the cutter (3 wood for a tree, 1 for a bush). A host cutting with peers connected does the same and adds its own wood. Applying a cut that is already there does nothing.
- `cut-join` a joining peer gets the cut list with the map params and replaces its cuts with it (`world.replace_cuts`): cuts it held that are not listed grow back, and none are doubled. Live cuts after that arrive on the same reliable channel, so they cannot overtake the list.
- `cut-join-parts` the join list goes at most `JOIN_CUTS_PER_MESSAGE` (500) cuts per message (#354, `WorldSave.split_changes`): the first part rides in `receive_map_params`, the rest follow at once as `receive_join_cuts(cuts)`, which the joiner adds with `world.restore_cuts`. 500 cuts encode to about 35 KB, so one message stays bounded however many cuts the world holds, and the joiner still gets every cut with its age. `receive_join_cuts` is an authority RPC and its handler also drops any message whose sender is not peer 1.
- `cut-regrow` the host runs `TileMap.regrow_due` as offline (its own play time, the type's `regrow_delay`, a stump under any player or mob waits, #232) and sends every peer one `apply_regrow_cells(cells)` per tick listing every stump that regrew in it (`TileMap.plants_regrown` -> `Interaction._on_plants_regrown`; see [Regrowth sync messages](./regrow-sync.md), #353). A peer applies it at once with `TileMap.grow_back` for each cell, whatever its own age for that cut; a cell it holds no cut on is left alone. A client's own `regrow_due` does nothing while connected, so its `regrow_delay` never counts. `apply_regrow_cells` is an authority RPC, so the host refuses one sent by a client (an engine error on the host, "not allowed"), and the handler also drops any message whose sender is not peer 1. It travels on the same reliable channel as `apply_cut` and the join list, so a regrowth cannot overtake the cut it ends.
- `cut-mode` interact mode and the mode button work in every session state: offline, hosting alone, hosting with a peer, connecting, connected.
- `cut-join-age` the join list carries each cut's age, so a late joiner's saved cuts age like the host's; its stumps still regrow only when the host sends `apply_regrow_cells`. A regrown cell is simply not in the list, so the joiner draws the plant from the map.
- Not synced: the inventory itself. Plank bridges sync separately ([Build sync](./build-sync.md), #297).

## How to get to it (user POV)

- Instance A: Host. Instance B: Join. On either, switch to interact mode and chop a tree or bush; the stump shows on both and the player can walk through it on both.

## Driving it with verify-flagoria helpers

Preconditions: `doctor.sh` exits `0`. Time cost: `-- test_cut_sync_two_players` about 2.4 s in `tools/verify.sh` (~3.7 s alone with `--only=`); `-- test_cut_replace` about 0.2 s and `-- test_interact_in_multiplayer` about 0.3 s (~1.5 s and ~1.6 s alone); the stress run `python3 tools/stress_netcode.py -n 10 --only cut_sync_two_players` about 18 s (4 runs at a time). `-- test_regrow_sync_two_players` (#298) about 10 s in `tools/verify.sh` (~9.8 s alone with `--only=`; 6 s of it is the host's regrow delay); its stress run `python3 tools/stress_netcode.py -n 10 --only regrow_sync_two_players` about 35 s (4 runs at a time, worst run 10.4 s).

- **Run (headless).** `godot --headless --path . --script res://tests/run_tests.gd -- --only=cut_sync_two_players` (also `cut_replace`, `interact_in_multiplayer`, `cut_save_late_join`, `regrow_sync_two_players`, `join_cuts_split`, `join_cuts_host_only`), or the full `tools/verify.sh`. Stress: `python3 tools/stress_netcode.py -n 10 --only cut_sync_two_players`.
- **What the scenario does.** `tests/net/test_cut_sync.gd` starts three headless processes of `tests/cut_sync_probe.gd` on seed 7: a host, a client, then a late joiner. The host and the client each cut a tree and a bush near the spawn at the same time, through `Interaction._cut` (the path a tap ends in) after stepping next to the cell. The probe writes its peer id, cut list, wood, errors and the state of each watched cell (`plant`, `decor`, `clear`) to a JSON file every 100 ms.
- **Proof.** `PASS test_cut_sync_two_players (host cut [...], client cut [...])`. It fails unless, within 20 s, the host and the client hold the same four cuts, each of those cells shows the same stump and is clear ground on both, and each has exactly 4 wood; then the late joiner holds the same four cuts and cell states; and no peer logged an engine error. `-- test_cut_replace` proves the join list is applied as the exact set and that a second cut of a cell does nothing.
- **Regrowth scenario.** `tests/net/test_regrow_sync.gd` runs the same probe with `--regrow=S` (that peer's map-wide delay; its player steps 64 px away after its cuts so it does not hold a stump back): a host with 6 s and clients with 1 s. The host cuts a tree and the client a bush; the client then sends the host a forged `apply_regrow_cells` (`PATH.forge`). Past the client's 1 s both stumps must still be on both peers. A first late joiner must get both cuts with the host's ages (within 0.5 s). When the host's 6 s are up, the host, the client and that joiner must show the same plants back, each cell's regrowth within 500 ms across the three (the probe logs when each cut left its list, in `regrown`), and a second late joiner must hold no cuts and show the same plants. The host's only allowed errors are its refusals of the forged RPC. Proof: `PASS test_regrow_sync_two_players (...)`, after a `regrowth spread across peers (ms)` line (a few ms locally).
- **Join list in parts.** `tests/net/test_join_cuts.gd` (#354) runs in one process with the `MultiplayerAPI` stand-in of `tests/net/test_regrow_batch.gd`. `-- test_join_cuts_split`: a host on seed 7 cuts 1,200 plants with ages 0-49 s and syncs peer 2; every recorded message must carry at most `JOIN_CUTS_PER_MESSAGE` cuts (a cap below 1,200, so the list is really split), encode to at most 64 KB, and list each cut once, and a client that applies them in order must hold exactly the host's cuts and ages. Proof: `PASS test_join_cuts_split (1200 cuts in 3 messages of [500, 500, 200], biggest 35584 bytes)`. `-- test_join_cuts_host_only`: `receive_join_cuts` from peer 3 or a local call (sender 0) adds nothing; from peer 1 it adds the cuts. Time cost: each about 0.2 s in `tools/verify.sh` (~1.8 s alone with `--only=`, against ~1.6 s for runner start-up); no network peer, so nothing in the Netcode stress job.
- **Drive (live).** None yet: a two-launch drive like the one in [Two-player Host/Join](./two-player-host-join.md) that taps a tree on each side is not written. The headless scenario runs the same game code from `Interaction._cut` on; only the tap and swing, covered by [Chop trees (live drive)](./chop-trees.md), are left out.

## Gotchas

- The probe moves its player next to each cell and waits 300 ms before the cut, so the host's copy of the player position is close enough for the reach check.
- The host decides from `predict_cell`, so a hand-drawn test map (`world.set_cell` on an empty map) has nothing the host will cut. In-process tests that tap trees on a hand-drawn row work offline only; use the seed-7 map for anything the host decides.
- In one process two `SceneMultiplayer`s on different roots do not share node paths, so the cut RPCs cannot be exercised in-process; `-- test_interact_in_multiplayer` checks only the mode and button there.
- The engine refuses a client's `receive_join_cuts` before the handler runs (authority RPC); the stand-in skips that check, which is what lets `test_join_cuts_host_only` reach the handler's own sender check.
